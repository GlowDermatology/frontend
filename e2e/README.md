# End-to-end suite

Playwright specs that drive the admin panel against a real backend. They are not part of `npm run check` or CI:
they need a running Django API in fake integrations mode with the demo dataset.

`seo-sessions.spec.ts` needs a backend with B-W1 (slugs, SEO texts and checklist, customer sessions; `feat/web-client`) and the storefront sign-up of B-W2. The suite needs the gap-closure backend: `feat/m3-gaps` at `4d4a5aa` or later (staff
management, specialists and services, category images, banner and campaign URLs). Before it, it needed the M3
backend: `feat/m3-integration` at `d4db5cf` or later (the same tree as `d9843de`, before the
branch was rebased). Against an M2 backend the M3 specs fail: «Bekor qilish» is not offered (no `cancelled_at`), the
no-Click-id specs expect M3's `conflict` and `manual_reason`, and the Google session gets no `auth_method`.

```bash
# backend (repository GlowDermatology/backend, M3), local settings with OAUTH_MODE=fake. Django reads os.environ only:
# export the .env first, or seed_demo silently falls back to the demo password instead of SEED_ADMIN_PASSWORD.
set -a; . ./.env; set +a
uv run python manage.py seed_demo --reset      # repeatable dataset; DEBUG or --force only
uv run python manage.py runserver 127.0.0.1:8000

# frontend, api mode, with the fake Google and Facebook sign-in (for account-social.spec.ts; skipped without it)
GLOWDERMA_DATA_SOURCE=api GLOWDERMA_API_URL=http://127.0.0.1:8000 GLOWDERMA_INTERNAL_SECRET=<INTERNAL_API_SECRET> \
  GLOWDERMA_ALLOWED_ORIGINS=localhost:3000 GLOWDERMA_COOKIE_SECURE=false \
  GLOWDERMA_OAUTH_PROVIDERS=google,facebook GLOWDERMA_OAUTH_MODE=fake GLOWDERMA_OAUTH_ALLOW_FAKE=true \
  npm run build && npm run start

# suite (E2E_BACKEND_DIR: the backend checkout, for the failed Click refund specs)
E2E_ADMIN_PASSWORD=<SEED_ADMIN_PASSWORD> E2E_BACKEND_DIR=../backend npm run e2e
```

Running the whole suite (all six projects) against a local stack: the backend `.env` needs, besides the local
defaults, `ADMIN_PANEL_URL=http://localhost:3000/admin` (e-mail link specs), `CAMPAIGN_APPROVAL_DELAY_MINUTES=0`,
`ESKIZ_FAKE_CODE=123456`, `EMAIL_MODE=fake`, `FAKE_PAYMENTS_ENABLED=true` and `PAYMENT_WEB_RETURN_URL` (the
`customer` project, see the main README "Customer website"); the frontend runs with the main README's variables plus
the fake OAuth ones above; the suite with `E2E_ADMIN_PASSWORD`, `E2E_STAFF_PASSWORD`, `E2E_BACKEND_DIR` and
`E2E_API_URL` set, so no arranging spec skips. `mfa.spec.ts`'s manager reset reads the badge from the staff list:
it needs the backend whose `StaffListItem` carries `mfa_enabled` (manager only). `deleteStaffAccounts` deletes the
accounts' sessions first (`AuthSession.staff` is `PROTECT`): every account a spec signed in with is removed too.
The panel asks about the recommended deep link of a promotion before its test / approval (not at draft save);
`notifications-approval.spec.ts` answers «Baribir saqlash» there (`catalog-helpers.ts saveAnyway`, which only answers
a question that opens). The forms ask "save anyway?" only when it is news — a create, the save that activates, a
field just emptied or a changed Uzbek source — and remember the answer for the browser session.

Helpers: `e2e/ui.ts` drives the kit controls (`selectOption`, `selectValue`, `fillDate` / `fillTime` /
`fillDateTime`, `pickDate`, `pickerValue`, `expectDisabledReason`); `helpers.ts toast(page, title)` finds a toast by
`[data-toast]` in either live region (successes in `role="status"`, warnings and failures in `role="alert"`; assert
the tone with `toHaveAttribute("data-tone", "warning")`). The specs run in Uzbek (no `gd_admin_language` cookie), so
their Uzbek labels are the `uz` texts of the copy modules.

The Yandex Delivery spec needs the phase-3 backend (`feat/yandex-delivery`) in its local settings with
`YANDEX_DELIVERY_MODE=fake` and `DEV_FEATURES_ALLOWED` (both the local defaults) and eager Celery: the dispatch
request runs the outbox, so the fake Yandex creates and accepts the claim in the runserver process, which also serves
the dev route (the fake keeps its claims in that process's memory; a restarted runserver forgets them and the route
answers 409). It needs `E2E_BACKEND_DIR` (no API places a paid Yandex order for a test, so `createPaidYandexOrder`
places one through `commerce.services.create_order` with a stored quote and pays it through `mark_paid`, as the seed
does) and `E2E_API_URL` (the dev route is a staff route of the Django API: the spec signs in there with
`E2E_ADMIN_EMAIL` / `E2E_ADMIN_PASSWORD` for a bearer token; the panel's own session is HttpOnly). Without either it is
skipped. `sections.spec.ts` probes `/admin/delivery-issues/alerts` once: against a backend without the delivery
exception queue «Muammolar» is skipped and the other sections ignore that poll's 502.

Since M3 the seed keeps two failed Click refunds of its own (№10100, whose fake Click still reports the payment paid,
and №10175, whose fake Click is "down"); the Click-down spec uses №10175 and leaves №10100 to staff. No API sets the
fake Click's switches, removes a payment's Click payment id or starts a campaign's send, so the specs arrange that
through the backend's management shell (`e2e/backend-shell.ts`, test-only, never imported by `src/`): it runs
`uv run python manage.py shell` in `E2E_BACKEND_DIR` with that directory's `.env` loaded. The Click specs take the
newest processing Click order the board lists whose paid Click payment still has `click_paydoc_id`
(`clickOrdersWithPaydoc`; an order a stopped run left without the id is passed over) and set its `metadata.fake.click`
to `{"refund": "failed", "status": "paid"}` (cancelling the order from the UI then leaves a failed Click refund whose
status check answers "paid"; `"reversed"` and `"down"` are the other answers), or drop `click_paydoc_id` from its
payment's `provider_state`. The refused-cancel spec moves its own campaign between `scheduled` and `sending`
(`setCampaignState`); the approval specs give the customer a pushable device (`ensurePushableDevice`), run the
campaign beat once (`runCampaignBeat`: `start_due_campaigns` + `finalise_stopping_campaigns`, eager Celery, fake FCM),
leave a campaign mid-send (`startCampaignSendPartially`: the shell runs without eager Celery, so only the first batch
goes out and the next waits in the outbox), deliver the outbox (`runCampaignOutbox`: `core.dispatch_outbox`) and
create the ordinary staff account (`ensureStaffAccount`). Run the backend with `CAMPAIGN_APPROVAL_DELAY_MINUTES=0`
for them (production refuses below 5; locally 0 is allowed). The backend must run its local settings (fake integrations, eager Celery), on the same machine
as the suite.

Since the approval workflow a campaign is a draft until a superuser tests and approves it, so the specs' drafts are
never sent; the ones they approve are requested for 31 December 9999 (the furthest date the API accepts, so no beat
reaches them) and cancelled by the spec, except the beat spec's, which is meant to be sent (to the customer's fake
device only, fake FCM) and the stop spec's, whose first batch reaches 25 seeded fake devices. An `afterEach` removes
from the history any row titled `e2e qoralama …` / `e2e tasdiq …` (cancels a waiting one, returns it to draft, deletes
the draft; a sent or stopped one stays), so a failed run leaves nothing waiting. Only a run
killed before its cleanup (or before the refused-cancel spec moved its campaign back from `sending`) leaves one:
remove it from the history, or reset with `seed_demo --reset`. Likewise the social spec

The store settings, contacts and legal texts are no longer edited in `/admin/settings`: they moved to the Django ops
console (2FA, audited, allow-listed IPs; the page only links there through `GLOWDERMA_OPS_CONSOLE_URL`), so the former
`settings-legal.spec.ts` was removed; the backend tests that console.

On a fresh dataset every spec runs; from the second run on the retry spec is skipped, and after a few runs the
cancel spec falls back to Click orders and the payments and appointments specs are skipped until the next
`seed_demo --reset` (the seed has a handful of processing Payme orders and three requested visits); the Click specs
take four processing Click orders per run (the seed has six outside the design orders) and are skipped once none with
a Click payment id is left.

`e2e/.auth/` (git-ignored). Browsers: the pinned `@playwright/test` uses the Chromium build that ships with Playwright
